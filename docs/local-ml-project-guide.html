$Days 3�4 � Wire retrieval into the model

# retrieval + generation
import groq

client = groq.Client(api_key='YOUR_KEY')  # reads RAGBOT_GROQ_API_KEY from env in your app

def ask(question, k=4):
    q_emb = embedder.encode(question).tolist()
    results = collection.query(query_embeddings=[q_emb], n_results=k)
    context = "\n\n".join(results["documents"][0])

    prompt = f"""Answer using ONLY the context below. If the answer isn't there, say so.

Context:
{context}

Question: {question}"""

    response = client.chat.completions.create(
        model="openai/gpt-oss-20b",
        messages=[
            {"role": "system", "content": "Answer using ONLY the context below. If the answer isn't there, say so."},
            {"role": "user", "content": prompt},
        ],
    )
    return response.choices[0].message.content
Common trap: without "answer only from context" instructions, even Groq will lean on its own trained knowledge instead of your documents. Test this explicitly with a question your documents don't cover.

Why style, not facts: fine-tuning is a poor tool for teaching a model new information on a CPU budget � RAG already does that job. Fine-tuning a small model for a few hundred steps is well suited to changing how it responds, not what it knows.
Note on Groq vs. this step: Groq is a hosted API, so you can't LoRA fine-tune it locally � Week 2's fine-tune targets a small open-weight model (e.g. Qwen2.5-1.5B) you download and train yourself. Groq stays the Week 1 generation engine; this is a separate side-by-side experiment.

Guidelines: Groq API + local CPU work

API rate limits

Free-tier Groq keys cap requests per minute/day. Add basic retry/backoff around chat.completions.create calls, and batch your test-question runs so you don't hit limits mid-demo.

Context length

Groq handles long context well, but keep retrieved chunks tight (3�5 short passages) anyway � it's faster, cheaper, and keeps the model focused on your documents instead of padding.

Fine-tuning patience (local only)

A few hundred examples at low LoRA rank might take 1�4 hours on CPU for the Week 2 local model. Kick it off before bed or before a work block � don't sit and wait.

Embeddings are cheap

The embedding model (~80MB) runs entirely locally and is far lighter than any generation model � don't hesitate to re-embed your whole document set if you change chunking strategy.

Model size (Week 2 fine-tune)

Stay at 1�3B params for the local fine-tune target. A 7B model at Q4 quantization is usable if you're patient; larger models will feel broken, not just slow.

Quantization formats (Week 2 fine-tune)

Q4_K_M is a solid default balance of speed and quality for CPU. Q8 is noticeably slower with modest quality gains at this model size.
